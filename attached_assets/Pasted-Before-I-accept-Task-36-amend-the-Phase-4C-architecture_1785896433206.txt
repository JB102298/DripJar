1. COMMITMENT SNAPSHOT MUST PRESERVE SOURCE PROVENANCE
==================================================

The current plan has a contradiction.

It says:

- commitment snapshot stores refundablePrincipalCents
- confirmation rejects if current refundable differs from snapshot

But it also says:

- if a new Drip arrives after the snapshot, the contributor should still be able to commit the previously-reviewed amount
- the new Drip must remain refundable

Those requirements cannot be satisfied safely using only a snapshot total.

Example:

At preview:
Drip A refundable = $100

Snapshot:
$100

After preview:
Drip B succeeds for $50

Current refundable:
$150

The user reviewed and acknowledged only $100.

Correct behavior:
- allow commitment of the original $100
- Drip B's $50 remains refundable
- do NOT silently commit $150
- do NOT reject merely because the total increased

Therefore add SOURCE-LOT SNAPSHOT PROVENANCE.

Preferred design:

Add:

commitment_snapshot_allocations

Fields conceptually:

id
commitment_snapshot_id
source_financial_transaction_id
principal_cents
created_at

At commitment-preview time:

1. Lock/read current financial state consistently.
2. Determine the FIFO refundable Stripe-backed source lots that make up the previewed refundable amount.
3. Persist those exact source allocations with the snapshot.
4. Snapshot amount = SUM(snapshot allocations).

At confirmation:

- lock jar_members
- validate snapshot owner/jar/version/expiry/status
- verify every snapshotted allocation is STILL refundable and unreserved/uncommitted
- do NOT require total current refundable == snapshot amount
- require that the exact snapshotted source amounts remain available

If new principal arrived after preview:
- it is not present in commitment_snapshot_allocations
- therefore it remains refundable

If part of the snapshotted principal was refunded/reserved/otherwise consumed before confirm:
- reject 409 balance_changed / snapshot_stale
- require a fresh preview

fund_commitment allocations should be copied/derived from the validated snapshot allocations rather than recomputed from the current global FIFO pool.

This guarantees the explicit acknowledgement applies only to money that existed when the user reviewed the commitment.

Update schema/migration plan accordingly.

This likely means an additional table or combining it cleanly into migration 0013/0014.

2. SNAPSHOT IDEMPOTENCY SEMANTICS
==================================================

The current plan says a second confirmation of an already-consumed snapshot returns 409, while also saying snapshotToken is the idempotency key.

For a true idempotent confirmation endpoint:

If:

snapshotToken was already successfully consumed
AND
the authenticated user/jar matches
AND
a fund_commitments row exists for that snapshot/idempotency key

then a harmless client retry should return the EXISTING successful commitment result.

Do NOT execute another commitment.

Do NOT return 409 for an exact retry of a successful request.

Use 409 for:
- expired snapshot
- stale snapshot
- snapshot belongs to different user/jar
- snapshot invalidated before successful commit

But successful duplicate request using the same snapshotToken should be idempotent.

Add tests.

4. REFUND REQUEST AGGREGATE STATUS
==================================================

One refund request may allocate across multiple original Stripe payments.

Example:

Refund request = $175
Drip A refund allocation = $100
Drip B refund allocation = $75

Therefore refund_requests.status cannot simply become completed or failed based on the first allocation webhook.

Define deterministic aggregate behavior.

Recommended:

pending_provider
processing
completed
partially_failed
failed
cancelled

Or an equivalent model that represents mixed allocation outcomes.

Rules:

- completed only when ALL allocations succeeded
- failed only when no allocation succeeded and terminal failure occurred
- partially_failed when some succeeded and some failed/canceled
- processing while at least one allocation is non-terminal

Do not hide partial provider outcomes.

The balance API must accurately reflect:
- amount still refund-pending
- amount refunded
- amount returned to refundable because an allocation failed

Activity/UX must not say "Refund Completed" if only part succeeded.

==================================================

Reservation may span multiple source FTs.

Every refund allocation owns its own reserved principal amount.

On provider success for allocation X:

REFUND_CLR CR

Do not reverse or finalize the entire refund_request amount when only one allocation changes status.

Every allocation transition must be idempotent.
