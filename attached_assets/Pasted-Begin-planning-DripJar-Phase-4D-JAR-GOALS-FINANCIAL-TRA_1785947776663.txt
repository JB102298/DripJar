==================================================
PHASE 4D PRODUCT GOAL
==================================================

Make the Jar's financial state understandable and actionable for normal users.

Phase 4D has TWO major components:

A. JAR GOALS
B. FINANCIAL TRANSPARENCY UX

Jar Goals are planning categories INSIDE one Jar.

Examples:

Vacation Jar — $10,000 total

Goals:
Flights        $2,500
Hotel          $3,500
Rental Car     $1,000
Activities     $1,500
Spending Money $1,500

These goals DO NOT represent:

- separate Stripe balances
- separate bank accounts
- separate ledgers
- separate custodial accounts
- separate payout destinations

There is still ONE actual Jar financial balance.

Goals answer:

"What are we saving this Jar's money for?"

==================================================
1. JAR GOALS — CORE BUSINESS RULES
==================================================

Jar Goals should be OPTIONAL.

A Jar may have:

- no named goals
OR
- one or more named goals

If no goals exist, existing Jar behavior continues normally.

Each goal should conceptually include:

- id
- jarId
- name
- description optional
- targetPrincipalCents
- priority/order
- status
- createdAt
- updatedAt

Potential statuses:

active
completed
archived

Do not over-engineer workflow states unless needed.

Organizer controls goal creation/editing/order.

Members can view goals.

For MVP, members do not create/edit Jar Goals unless existing product permissions clearly justify it.

==================================================
2. TOTAL GOAL AMOUNT VS JAR TARGET
==================================================

Audit the current Jar goal/target amount field.

We need a deterministic rule between:

Jar target principal
and
sum of active named Jar Goals

Preferred MVP invariant:

SUM(active goal targetPrincipalCents)
must equal the Jar's total target principal.

Example:

Jar target:
$10,000

Goals must total:
$10,000

Do NOT silently allow:
Jar target = $10,000
Goals = $8,000

unless there is an intentional "Unallocated" bucket.

Preferred UX:

If named goals total less than Jar target, automatically show:

Unallocated
$2,000

as a CALCULATED display bucket, not necessarily a persisted goal row.

This gives us flexibility while keeping the Jar target authoritative.

Audit which model is cleaner:

A.
Require named goals to equal Jar target exactly

OR

B.
Allow named goals ≤ Jar target and compute:
Unallocated Target = Jar target − named goal targets

My preference is B.

But named goals must NEVER exceed Jar target.

==================================================
3. GOAL FUNDING MODEL — DETERMINISTIC WATERFALL
==================================================

For MVP, do NOT let users manually assign each Drip to a goal.

Do NOT split Stripe contributions at payment time.

Do NOT add per-goal payment routing.

Instead:

Use a deterministic priority waterfall based on CURRENT ELIGIBLE JAR PRINCIPAL.

Example:

Goals by priority:

1. Flights — $2,500
2. Hotel — $3,500
3. Rental Car — $1,000

Current eligible principal:
$4,000

Display:

Flights:
$2,500 / $2,500
FUNDED

Hotel:
$1,500 / $3,500

Rental Car:
$0 / $1,000

This is planning allocation only.

No ledger movement occurs when a goal becomes funded.

No financial_transaction should be created merely because the waterfall changes.

==================================================
4. WHICH PRINCIPAL FUNDS GOALS?
==================================================

This requires careful architectural review.

We currently track:

- refundable principal
- committed principal
- refund pending
- refunded principal

For planning progress, decide which balance should count toward Jar Goals.

My preferred distinction:

TOTAL SAVED / CURRENT JAR PRINCIPAL:
refundable + committed + refundPending

But:

AVAILABLE / SECURELY COMMITTED:
committed only

Refund-pending principal is technically still in the refund process and should probably NOT be displayed as safely available for goals.

Therefore I currently prefer:

Goal funding progress =
refundablePrincipal + committedPrincipal

EXCLUDE:
- refundPending
- refunded
- fees
- processing fees

But I want the architecture plan to assess this carefully.

We may want TWO conceptual progress values:

Saved toward goal:
refundable + committed

Locked toward goal:
committed only

Example:

Flights target:
$2,500

Saved:
$2,500

Committed:
$1,800

This lets the UI communicate:

"Fully saved"
but
"$700 still refundable"

Do NOT change ledger semantics merely to support goal UI.

9. COMPLETED GOALS
==================================================

Goal "completed" should ideally be DERIVED when:

allocatedSavedPrincipal >= targetPrincipalCents

Do not require organizer to manually mark a fully funded goal complete.

If a refund later drops allocated principal below target:
the goal should become not-fully-funded again.

Therefore distinguish:

Funding state:
derived

Administrative state:
active / archived

Preferred:

Persist only:
active
archived

Derive:
unfunded
partially_funded
funded

Do not persist a mutable "completed" state that can drift.
