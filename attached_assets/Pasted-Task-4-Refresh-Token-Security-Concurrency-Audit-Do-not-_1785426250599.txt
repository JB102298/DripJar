Phase 2 — Security Evaluation

Evaluate the implementation against current OAuth-style refresh-token best practices.

Specifically answer:

* Can two simultaneous refresh requests both succeed?
* Can a rotated refresh token be reused?
* What happens if the response containing the new refresh token is lost?
* Does replay detection exist?
* Are sessions isolated per device?
* Is there a token family concept?
* Are refresh tokens ever logged?
* Are hashes compared safely?
* Can replay on one device revoke every device?

Then recommend one policy.

Preferred policy:

* One token family per device
* Rotation every refresh
* Replay revokes only the affected family
* Password reset revokes every family
* Logout revokes current family
* Logout-all revokes every family

If another policy is safer given the current architecture, explain why.

⸻

Phase 3 — Implementation

Only after the audit.

Implement improvements only where necessary.

If a schema change is required:

Create

0003_refresh_token_security

Do not modify previous migrations.

Requirements:

Atomic rotation

Within one database transaction:

* Locate session
* Lock row
* Validate
* Revoke old session
* Create replacement
* Commit
* Return tokens

Exactly one concurrent refresh may succeed.

⸻

Replay detection

Reusing a rotated token must:

* Detect replay
* Revoke the affected token family
* Record revoke reason
* Return generic Unauthorized

Do not leak security details.

⸻

Network-loss behavior

Document the behavior when:

* Server rotates token
* Response never reaches client
* Client retries old token

Either:

* Keep strict one-time rotation

OR

Implement a carefully justified retry window.

Do not weaken replay protection.

⸻

Mobile client

Verify:

* One refresh mutex
* One refresh request
* One retry
* SecureStore cleared on terminal failure
* No infinite refresh loop
* No token logging
* Graceful reauthentication after revoked family
