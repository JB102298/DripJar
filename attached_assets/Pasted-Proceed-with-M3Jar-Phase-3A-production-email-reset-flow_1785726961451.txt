PART 2 — PASSWORD RESET EMAIL

Recommended function:

Use the same Resend client abstraction/pattern already used for invitation emails.

Reset URL format:

{APP_BASE_URL}/reset-password/{rawToken}

Requirements:

* Do not log or expose hashed token values.
* The email must contain the raw reset token only inside the reset URL sent to the intended recipient.
* HTML email should use M3Jar branding.
* Include a clear expiration statement matching the backend’s actual 1-hour expiration.
* Include a plain-text email alternative if the Resend implementation supports text + html together.
* The link should be clearly presented both as a button and as a fallback URL.
* Do not imply the password has already changed.
* Tell the recipient to ignore the email if they did not request a reset.

PART 3 — WIRE FORGOT-PASSWORD TO EMAIL DELIVERY

In artifacts/api-server/src/routes/auth.ts:

Wire the existing POST /auth/forgot-password flow to sendPasswordResetEmail().

Preserve all existing security properties:

* anti-enumeration behavior
* identical client response whether the email exists or not
* SHA-256 token storage
* 1-hour expiration
* existing rate limits
* no raw token persistence
* existing session revocation behavior during successful reset

IMPORTANT:

Email delivery failure must NOT reveal whether an account exists.

Preferred behavior:

* Generate/store reset token for a valid user.
* Attempt email delivery.
* Log an operational email-delivery error without including the raw token in production logs.

* DEV_SHOW_RESET_TOKEN may expose the raw reset token only when the application is running in a non-production environment.
* If NODE_ENV=production, DEV_SHOW_RESET_TOKEN must never cause the token to be returned.
* Do not log raw reset tokens in production.
* If raw-token logging remains in development for convenience, gate it explicitly on non-production execution.
