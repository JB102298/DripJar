GOAL

Complete the non-financial social/account lifecycle of M3Jar before beginning automation and real-money phases.

A user should be able to:
- create and manage a Jar
- invite people
- register from an invitation and complete joining
- see/manage invitations
- leave a Jar
- remove members when authorized
- edit Jar settings
- cancel/archive a Jar
- change their password
- verify their email address

All functionality must work end-to-end across database, API, mobile/web UI, authorization, activity logging, notifications/email where appropriate, and automated tests.

PART 1 — ORGANIZER INVITATION MANAGEMENT

Implement organizer-facing invitation management.

Required capabilities:

1. Organizer can view all invitations sent for a specific Jar.
2. Show at minimum:
   - invitee email
   - status
   - created date
   - expiration
   - contribution target if applicable
3. Organizer can cancel/revoke a still-pending invitation.
4. Revoked invitations can no longer be accepted.
5. Already accepted invitations cannot be revoked in a way that removes the member.
6. Expired invitations remain visibly distinct where appropriate.
7. Authorization:
   - only the Jar organizer may manage sent invitations
   - ordinary members must not be able to list or cancel organizer invitations
8. Log an activity event when an invitation is revoked if consistent with the current activity model.

Use existing invitation-token security patterns.

Do not expose raw invitation tokens in organizer listing responses.

PART 2 — INVITE → REGISTER → AUTO-JOIN FLOW

Fix the incomplete new-user invitation journey.

Current behavior:
Unauthenticated invitees must register/login and manually reopen the invitation link.

Required behavior:

1. User opens:
   /invite/{token}

2. If signed out:
   - preserve the invitation token safely for the authentication flow
   - allow user to choose login or registration
   - after successful authentication/registration, automatically return to the invitation flow

3. User should then be able to accept the invitation without manually reopening the email.

4. Registration must NOT automatically accept the invitation without the user's explicit acceptance unless the existing product UX clearly already communicates acceptance.

5. Avoid persisting invitation tokens longer than necessary.
6. Do not log invitation tokens.
7. Handle:
   - expired token
   - revoked token
   - already accepted token
   - invitation email belonging to a different authenticated account

Do not weaken current invitation security.

PART 3 — LEAVE JAR

Implement member-initiated leaving.

Requirements:

1. Non-organizer member can leave a Jar.
2. Organizer cannot use "leave" to abandon ownership.
3. Authorization must be enforced server-side.
4. Determine what should happen to:
   - jar_members row/status
   - contribution schedules
   - agreement acceptances
   - notifications
   - activity history
   - existing simulated contributions

Prefer preserving historical/audit records rather than destructive deletion.

If schema changes are required, use explicit lifecycle/status fields rather than deleting financial/history rows.

Since contributions are currently simulated only:
- do not invent real refund behavior
- clearly preserve historical simulated contribution records

Add member-facing UI with a confirmation step.

PART 4 — REMOVE MEMBER

Implement organizer member removal.

Requirements:

1. Only organizer may remove another member.
2. Organizer cannot remove themselves through this action.
3. Removed member loses active access to the Jar.
4. Preserve historical activity/contribution records.
5. Define and implement behavior for their:
   - active schedule
   - agreement acceptance
   - notifications
   - membership record/status

6. Log removal in activity.
7. Notify the removed member in-app if consistent with notification architecture.

Add organizer UI from the Members area.

Include confirmation before removal.

PART 5 — MEMBERSHIP LIFECYCLE MODEL

Before implementing Parts 3–4, inspect whether jar_members currently supports lifecycle states cleanly.

If it currently assumes membership rows are permanently active:

Design the smallest safe schema change needed to represent:
- active
- left
- removed

Prefer status + timestamp fields such as:
- membership status
- left/removed timestamp

Do not hard-delete membership history unless there is a strong existing architectural reason.

Create a new numbered Drizzle migration if schema changes are necessary.

All Jar access checks must treat only active membership as granting access.

Review getJarAccess and every route relying on membership.

Add tests proving left/removed members cannot regain Jar access through stale endpoints.

PART 6 — JAR SETTINGS UI

The PATCH /api/jars/:jarId API already exists.

Implement the missing Settings UI.

Organizer should be able to edit fields that the backend safely supports, including appropriate existing Jar properties such as:
- name
- description
- target/event date
- other currently editable settings

Do NOT casually allow changes to financial/member obligations if doing so would create inconsistent contribution targets, agreements, milestones, or schedules.

Audit each editable field before exposing it.

If a field requires recalculating participant obligations, do not implement a naive frontend-only recalculation.

Report any fields intentionally left immutable and why.

PART 7 — CANCEL / ARCHIVE JAR

The backend already has POST /jars/:id/cancel.

Complete the user flow.

Requirements:

1. Organizer-only UI action.
2. Explicit confirmation.
3. Clearly explain consequence.
4. Cancelled Jar becomes non-active.
5. Members should no longer be able to create simulated contributions or modify active schedules on a cancelled Jar.
6. Historical data remains viewable if the architecture supports it.
7. Add activity and notification behavior where appropriate.
8. Ensure API-level state guards exist — do not rely on hiding buttons.

Audit whether "cancelled" and "archived" should remain distinct concepts.

Do not add hard deletion in this phase.

PART 8 — PASSWORD CHANGE

Implement authenticated password change.

Backend requirements:

1. Require current password.
2. Require new password meeting existing password policy.
3. Verify current password using existing bcrypt patterns.
4. Update the password hash.
5. Revoke existing refresh sessions after successful change.

Choose and document whether:
- current session survives, or
- all sessions including current are revoked and user must sign in again.

Prefer the option that best matches the existing security architecture.

6. Rate-limit appropriately.
7. Never log passwords.
8. Return generic safe errors.

Frontend:
- add Change Password under profile/settings
- current password
- new password
- confirm new password
- loading/error/success states

Add tests.

PART 9 — EMAIL VERIFICATION

Implement email verification end-to-end.

Current state:
users.emailVerified exists but is unused.

Requirements:

1. Generate a cryptographically random verification token.
2. Store only a hash of the token.
3. Give tokens a defined expiration.
4. Verification tokens must be single-use.
5. Send an M3Jar verification email using the existing Resend abstraction.
6. Add public verification route/screen.
7. Allow resend-verification with rate limiting.
8. Preserve anti-enumeration principles where appropriate.
9. Mark emailVerified only after successful token validation.
10. Do not log raw verification tokens in production.
11. Development-only token exposure, if added for testing, must be guarded exactly like password-reset dev behavior.

DATABASE:
If verification-token hash/expiry fields do not exist, add them via migration.

PRODUCT BEHAVIOR:

Do NOT suddenly block all existing app use based on emailVerified unless explicitly necessary for this phase.

Instead:
- implement the verification system
- visibly show verification state
- prompt unverified users to verify
- identify any sensitive actions that should eventually require verification

For invitation handling:
carefully prevent an authenticated user from using an invitation addressed to another email.

Add automated coverage.
