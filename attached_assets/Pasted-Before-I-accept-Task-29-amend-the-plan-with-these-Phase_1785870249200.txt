1. PROCESSING-FEE GROSS-UP

The current Part C fee calculation is not sufficient.

Do NOT calculate the customer processing fee only from:

principal + DripJar fee

and then simply add that result to the charge.

Stripe assesses its percentage against the FINAL Stripe charge amount, which includes any processing-fee amount DripJar adds.

DripJar's intended rule is:

- Jar principal must remain fully intact
- DripJar 3% service fee is separate
- customer pays the estimated provider processing cost separately
- processing cost must not reduce Jar principal

Define:

baseCents =
  principalCents + dripJarFeeCents

totalChargeCents =
  baseCents + processingFeeEstimatedCents

processingFeeEstimatedCents must be the MINIMUM integer-cent amount such that:

processingFeeEstimatedCents >=
  computeStripeFeeOnCharge(totalChargeCents, paymentMethodType)

Use integer-cent arithmetic and explicit rounding.

For cards:

providerFee(total) =
  half-up(total * 290 / 10_000) + 30 cents

For ACH:

providerFee(total) =
  min(
    half-up(total * 80 / 10_000),
    500 cents
  )

The implementation should solve/gross-up the fee deterministically.

Do not use floating-point dollars.

Add tests including the $200 principal example:

DripJar fee: $6.00

CARD:
Processing estimate should be approximately $6.46
Total approximately $212.46

Verify using the actual integer algorithm rather than hard-coding those numbers.

ACH:
Processing estimate should be approximately $1.66
Total approximately $207.66

Again verify through the actual algorithm.

Also test:
- ACH cap boundary
- card fixed-fee behavior
- very small payments
- rounding boundaries
- large safe values

processingFeeActualCents remains separate from the original estimate so future reconciliation can show variance.

Do not mutate principal or DripJar fee during reconciliation.
