PART 1 — CUTOFF DATE MODEL

Audit the current Jar lifecycle and agreement language.

Introduce the smallest safe schema/model change needed to represent a real cutoff date.

Determine whether the cutoff should be:

- explicitly set by organizer
- derived from target/event date
- or support both with an explicit stored value

Prefer an explicit persisted cutoff timestamp/date that can be validated independently.

Requirements:

1. Add a cutoff field to the Jar model if none exists.
2. Validate:
   - cutoff must be before the event/target date where applicable
   - cutoff cannot be nonsensical relative to current date when creating/launching
3. Define exact semantics for:
   - Draft
   - Inviting
   - Saving
   - Commitment
   - Cancelled
   - Completed
4. Decide whether Commitment is a stored status transition or a derived phase from cutoff time.
5. Avoid ambiguous dual sources of truth.

Document the chosen model clearly in code comments only where necessary.

Do not implement financial effects yet.

PART 2 — AGREEMENT ENFORCEMENT

The agreement system already stores versioned acceptances.

Add API-level rules so Jar activation/lifecycle behavior can rely on them.

Requirements:

1. Define which actions require an accepted current agreement.
2. At minimum, evaluate:
   - joining/remaining active in a Jar
   - creating/changing contribution schedules
   - simulated contribution creation
   - transition into Commitment phase
3. If all active members must accept the current agreement before a Jar can enter Commitment, enforce that server-side.
4. If agreement text/version changes:
   - previous acceptance must not silently count for the new version
   - user must re-accept where required
5. Do not rely on frontend visibility alone.
6. Return explicit safe API errors for blocked actions.
7. Add tests for outdated/nonexistent acceptance.

PART 3 — CUTOFF LIFECYCLE TRANSITION

Implement deterministic lifecycle behavior around the cutoff.

Choose the safest architecture between:

A. derived phase from current time + cutoff date
B. persisted status transition performed by automation

Avoid requiring two independent truths that can drift.

Requirements:

- before cutoff: Saving behavior
- at/after cutoff: Commitment behavior
- cancelled/completed states override derived phase
- expired/cutoff calculations must be timezone-safe
- use UTC consistently at the API/database layer

If automation performs a transition, make it idempotent and safe to run repeatedly.

Add tests around:
- just before cutoff
- exact cutoff instant
- just after cutoff
- cancelled Jar
- completed Jar

PART 4 — UPCOMING / MISSED CONTRIBUTION LOGIC

Audit the current contribution_schedules and reminder logic.

Implement a canonical server-side way to determine:

- next scheduled contribution
- due soon
- due today
- missed
- satisfied
- inactive schedule

Requirements:

1. Do not trust the frontend to determine whether a contribution is missed.
2. Base state on:
   - schedule
   - due date
   - actual simulated contribution records
   - membership state
   - Jar lifecycle
3. Define how a contribution satisfies a scheduled obligation.
4. Prevent double-counting one contribution across multiple schedule periods.
5. Handle weekly, bi-weekly, monthly, and twice-monthly schedules consistently.
6. Use integer cents.
7. Do not invent real payment settlement semantics yet.

Expose this information through existing or new API responses as appropriate.

   - contribution missed
   - upcoming cutoff
   - cutoff reached

3. Create in-app notifications only once per logical reminder event.
4. Record sufficient metadata/idempotency state to prevent duplicate delivery.
5. Use database transactions where appropriate.
6. Do not rely solely on in-memory state.

If schema changes are needed for reminder deduplication, add them explicitly.
