1. WHAT IS REFUNDABLE

Only CONTRIBUTION PRINCIPAL is refundable.

Example:

Customer chooses:
$200.00 Jar principal

DripJar service fee:
$6.00

Payment processing:
$6.46 card example

Total charged:
$212.46

Before commitment:

Refundable principal:
$200.00

Non-refundable:
$6.00 DripJar fee
$6.46 processing fee

If the contributor requests a full refund before commitment:

Stripe refund amount:
$200.00

NOT:
$212.46

The DripJar fee remains non-refundable.

The customer-paid processing fee remains non-refundable from DripJar.

Principal refund must never reduce or reverse the original DripJar fee revenue or original processing-fee accounting.

2. EXPLICIT CONTRIBUTOR COMMITMENT

A cutoff date by itself MUST NOT make real principal non-refundable.

The contributor must explicitly take an action equivalent to:

"Commit My Funds"

Only the authenticated contributor may commit their own funded principal.

THE ORGANIZER MUST NEVER BE ABLE TO COMMIT ANOTHER CONTRIBUTOR'S MONEY.

Organizer role is irrelevant to ownership of another member's principal.

If a jar has five people with $2,000 each and four members commit:

Committed:
$8,000

Still refundable / awaiting commitment:
$2,000 belonging to the fifth contributor

Do not implement all-or-nothing jar commitment.

3. AGREEMENT VERSION

Commitment must be tied to the exact agreement/version the contributor is acknowledging.

The commitment record must preserve:

- jar
- member
- authenticated user
- agreement/version identifier
- amount committed
- timestamp
- acknowledgement/version context
- idempotency information

Do not infer commitment merely from agreement acceptance.

Agreement acceptance and FUND COMMITMENT are distinct actions.

4. SOURCE OF TRUTH

Refundability and committed balances must come from the immutable financial ledger.

Existing Phase 4A accounts include:

CTRB_REFUNDABLE
CTRB_COMMITTED

Existing primitives already include internal:

postRefundPrincipal
postCommitPrincipal

Audit them rather than reinventing the ledger.

Expected ledger movements:

COMMIT PRINCIPAL:

CTRB_REFUNDABLE  DR
CTRB_COMMITTED   CR

REFUND PRINCIPAL:

CTRB_REFUNDABLE  DR
REFUND_CLR       CR

Commitment does NOT create or destroy principal.

Refund removes refundable principal from DripJar liability.

Never mutate historical contribution ledger entries.

5. CONTRIBUTOR-ONLY SECURITY

Before exposing postCommitPrincipal publicly, enforce:

jar_members.id = requested memberId
AND
jar_members.userId = authenticated req.userId

Do not merely verify:
"caller is an active jar member."

Do not allow:

- organizer commits contributor
- organizer selects arbitrary memberId
- contributor commits another member
- client provides authoritative commit amount for another member

The server determines the authenticated member record.

Prefer no client-supplied memberId at all if unnecessary.

6. COMMITMENT AMOUNT FOR MVP

Public "Commit My Funds" should commit the contributor's CURRENT REFUNDABLE PRINCIPAL for the relevant agreement version.

Do not expose an arbitrary user-entered partial commitment amount in Phase 4C UI.

Example:

Funded refundable principal:
$1,350

User taps:
Commit My Funds

Server commits:
$1,350

If the contributor later adds another successful Drip after that commitment:

the NEW principal is refundable again until explicitly committed.

Do NOT automatically commit future contributions merely because the member previously committed.

This means a member may have multiple explicit fund-commitment events over time.

Internal ledger primitives may continue supporting partial amounts for accounting/testing.

9. STRIPE TEST MODE REFUNDS

Phase 4C remains STRICTLY Stripe TEST MODE.

Use Stripe's refund API.

A refund must be tied to the original Stripe-backed payment(s).

Do not invent a generic transfer of money back to the user.

Stripe supports partial refunds against a payment.

Because a member may have multiple successful Drips, define a deterministic allocation rule for an aggregate principal refund.

PREFERRED RULE:

OLDEST ELIGIBLE SUCCESSFUL DRIP FIRST (FIFO)

Reason:
- clear auditability
- minimizes risk of an older ACH contribution aging out of its provider refund window
- deterministic under retry

Example:

Drip A principal:
$100

Drip B principal:
$150

Refund request:
$175

Allocate:

Drip A:
$100 principal refund

Drip B:
$75 principal refund

Remaining refundable:
$75 from Drip B

Audit whether FIFO is straightforward with the current financial_transaction model.

If another allocation policy is materially safer, explain why before implementation.

10. REFUND ELIGIBILITY PER ORIGINAL PAYMENT

For each original successful Stripe TEST payment, track:

- original principal
- principal already refunded
- principal committed if allocation tracking requires it
- remaining provider-refundable principal
- PaymentIntent / Charge linkage
- payment method category
- provider refund status

Do not refund more principal through Stripe than remains refundable against that payment.

Do not allow aggregate member refund logic to over-refund a source PaymentIntent.

11. COMMITMENT ALLOCATION TO ORIGINAL DRIPS

This is important.

The ledger tells us the member's total refundable principal, but Stripe refunds operate against individual original payments.

Therefore Phase 4C needs a deterministic way to know which source contributions remain refundable.

Audit the cleanest model.

PREFERRED POLICY:

Commitment consumes refundable contribution lots OLDEST FIRST.

Example:

Drip A:
$100

Drip B:
$150

Member commits current $250:

A committed allocation:
$100

B committed allocation:
$150

If later a new Drip C adds $50:

C remains refundable until the contributor commits again.

If only $175 were internally committed in a future partial-capability scenario:

A $100 + B $75 would become committed.

Even though public MVP commits all current refundable principal, design the allocation layer so accounting remains deterministic.

The ledger remains monetary source of truth.

Contribution-lot allocation is the provider/refund provenance layer.

12. DO NOT REFUND COMMITTED PRINCIPAL

Once a principal amount is explicitly committed:

DripJar refund API must reject any attempt to refund it.

This must remain true even if Stripe technically still allows a refund.

Business-rule enforcement belongs in DripJar before calling Stripe.

15. ATOMICITY — REFUND

This is critical.

Avoid this failure:

Stripe refund succeeds
→ DB crashes
→ DripJar forgets refund
→ retry sends another refund

Use stable Stripe idempotency keys per refund allocation.

Design for:

- API retry
- process crash after Stripe success
- webhook retry
- DB transaction rollback
- multiple refund allocations
- concurrent refund requests

The provider refund and ledger refund must reconcile exactly once.

16. WHEN LEDGER REFUND IS POSTED

Plan carefully whether DripJar posts:

CTRB_REFUNDABLE DR
REFUND_CLR CR

when:

A. Stripe refund request is created

or

B. Stripe confirms successful refund

Preferred financial rule:

Do not mark principal as fully refunded until provider success is authoritative.

But once a refund request is accepted, that principal must be RESERVED so the contributor cannot:

- request another refund for the same dollars
- commit those same dollars while refund is pending

Therefore consider a reservation/pending-refund mechanism.

Do NOT solve this by prematurely treating pending provider refunds as completed ledger refunds.
